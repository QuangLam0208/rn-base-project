# base-react-native — Project Conventions

This file is auto-loaded context for Claude Code. It documents this
project's conventions so generated code matches the existing codebase
instead of reinventing patterns per session. See also
[README.md](README.md) for tech stack, setup, and a longer walkthrough.

## What this project is

A React Native + Expo **base project** combining [Ignite](https://github.com/infinitered/ignite)'s
stack (navigation, theming, i18n, MMKV, apisauce) with an MVVM
architecture (`BaseViewModel`, MobX) and InversifyJS dependency
injection — mirroring the Dagger 2 `AppComponent` used in the
`source-base-android` reference project (one composition root, one
`ApiService` gathering every endpoint, constructor injection
everywhere). It exists to be copied as a starting point for a new
project, not to be a real app: there is **no login/auth screen** and
**no business feature** — just the architecture, a single example tab
(`Home`), and a `Settings` screen (language/theme/OTA update).

`app/stores/authStore.ts` and `Api`'s Bearer-token attachment are kept
even though nothing sets a token yet — see "Auth infrastructure" below
for why, and what a real login screen would need to wire in.

## Folder structure

All application code lives under `app/` (not `src/`). Native code
(`ios/`, `android/`) is generated by `expo prebuild` — never hand-edit
it; edit `app.json`/`app.config.ts` and re-run prebuild instead.

```
app/
  di/
    container.ts                      # composition root — new Container() + container.load(...modules)
    types.ts                          # Symbol tokens for interface bindings
    useViewModel.ts                    # container.get() through a useState() hook, for screens
    modules/
      dataModule.ts                    # ContainerModule: StorageService/AuthStore/Api/ApiService/AppDatabase/RoomService/Repository
      viewModelModule.ts                # ContainerModule: ViewModel bindings
  viewmodels/base/BaseViewModel.ts   # shared MobX base — isLoading/error/runAction() + protected repository
  stores/authStore.ts                  # MobX singleton for cross-screen shared state, @injectable()
  screens/
    <ScreenName>/
      <ScreenName>Screen.tsx             # View + styles in one file — see below
      <ScreenName>ViewModel.ts            # all logic/state (MobX) — only if the screen has state
    Splash/SplashScreen.tsx               # stack, initialRouteName; resets straight to MainTabs, no gate
    Home/HomeScreen.tsx                   # the one example tab — copy this pattern for new screens
    Settings/SettingsScreen.tsx           # stack-pushed (not a tab); language + theme — see below, no ViewModel
  navigators/                           # AppNavigator (root stack: Splash/MainTabs/Settings) + MainTabNavigator (bottom tabs)
  components/                           # shared UI: Screen, Text, Button, Icon, TextField, ...
  theme/                                # colors, spacing, typography
  i18n/                                 # en.ts / vi.ts + translate() — Vietnamese is the default locale
  config/                               # env config (API_URL, MASTER_API_URL, exitRoutes, ...)
  data/
    Repository.ts                       # interface: { apiService; roomService; storageService } — see below
    AppRepositoryImpl.ts                 # @injectable() impl; property-injected onto BaseViewModel as repository
    remote/api/
      index.ts                          # apisauce Api client, @injectable(), attaches the Bearer token
      ApiService.ts                     # pure interface — deliberately empty, see below
      ApiServiceImpl.ts                 # @injectable() implementation — only the request() helper so far
      apiProblem.ts                     # normalizes apisauce errors into GeneralApiProblem
      master/
        MasterApiService.ts              # interface + impl for the second base URL — see the DI section
        MasterApiServiceImpl.ts           # below ("A second base URL")
    model/
      api/
        ResponseWrapper.ts, PageResponse.ts   # generic envelope DTOs — add item/, response/<domain>/ as you add endpoints
      room/UserEntity.ts                  # local SQLite row shape (scaffold, not wired to any screen yet)
    local/
      room/                                # AppDatabase/RoomService(Impl)/UserDao(Impl) — see below
      storage/                             # MMKV load/save/remove + StorageService (@injectable() wrapper)
  utils/                                 # date formatting, logging, crash reporting, etc. — no data-layer code here
```

## `ApiService`: interface + impl, one DTO per file

Mirrors `ai-project-android`'s split exactly: `data/remote/ApiService.java`
is a bare Retrofit interface (endpoint signatures only), and
`data/model/api/response/<domain>/XResponse.java` is one file per
response/request shape. This project does the same, but starts
**empty** — there is no real backend wired up yet:

- **`app/data/remote/api/ApiService.ts`** — a TypeScript `interface`,
  currently `export interface ApiService {}`. Add your first endpoint
  here as a method signature (`getSomething(): Promise<SomethingItem[]>`).
  **No apisauce calls, no mapping logic, no type declarations here** —
  if you're writing `this.api.apisauce...` or `export interface
  XItem`/`export interface XResponse` in this file, it's in the wrong
  file.
- **`app/data/remote/api/ApiServiceImpl.ts`** — the `@injectable()`
  class that implements `ApiService`. Currently has only `request()`
  (`protected`), a reusable "unwrap an apisauce response or throw"
  helper every endpoint method should go through — see its own doc
  comment for a worked example of adding a real endpoint (one apisauce
  call + one DTO→domain-model mapping per method).
- **`app/data/model/api/item/<Name>Item.ts`** (create this folder as
  you add endpoints) — the domain shape a method returns to screens,
  one per file, imported by both `ApiService.ts` (the return type) and
  `ApiServiceImpl.ts` (the mapping target).
- **`app/data/model/api/response/<domain>/`** (create as needed) — the
  wire-shape DTOs, one interface per file (e.g.
  `response/mentor/MentorResponse.ts`). Common envelopes
  (`ResponseWrapper<T>`, `PageResponse<T>`) already sit directly under
  `data/model/api/`. **Don't inline a response shape as an unexported
  `interface` inside `ApiServiceImpl.ts`** — give it its own file here,
  even for a one-off endpoint.

Adding a new endpoint: add its DTO(s) under `data/model/api/response/`,
add a `data/model/api/item/<Name>Item.ts` if it returns a new domain
shape, add the signature to `ApiService.ts`, implement it in
`ApiServiceImpl.ts`. Nothing else to wire — every ViewModel already
has `this.repository.apiService` (see the next section).

## `Repository`/`AppRepositoryImpl`: the facade every ViewModel gets

Mirrors `ai-project-android`'s `Repository.java`/`AppRepository.java`:
one object bundling `ApiService`, `RoomService`, and `StorageService`
(this project's equivalent of Android's `PreferencesService` —
MMKV-backed shared-prefs-style storage), so `BaseViewModel` only has
to property-inject one thing (`repository`) instead of a separate
field per service. A ViewModel calls an endpoint via
`this.repository.apiService.getX()`, local storage via
`this.repository.roomService.userDao()...`, and shared prefs-style
storage via `this.repository.storageService...` — never inject
`ApiService`, `RoomService`, or `StorageService` directly into a
ViewModel.

- **`app/data/Repository.ts`** — pure interface: `{ readonly
  apiService: ApiService; readonly roomService: RoomService; readonly
  storageService: StorageService }`. No logic (same "interface + impl"
  split as `ApiService`).
- **`app/data/AppRepositoryImpl.ts`** — the `@injectable()`
  implementation. `apiService` and `storageService` are normal
  constructor-injected fields (`StorageService`/MMKV has no Jest
  problem — see `data/local/storage/storage.test.ts` — so it's eager like
  `apiService`). `roomService` is a **lazy getter** — it does not
  construct `RoomServiceImpl` (and therefore does not open the real
  `expo-sqlite` connection) until something actually reads
  `repository.roomService`. This is deliberate: `BaseViewModel` gives
  *every* ViewModel a `repository`, and `expo-sqlite` has no Jest mock
  (see the Local database section below) — an eager `roomService` here
  would crash every single ViewModel test the moment `new
  AppRepositoryImpl()` ran, not just the ones that actually touch
  local storage. `AppRepositoryImpl.test.ts` is what proves this
  laziness holds, not just a comment — it asserts `openDatabaseSync`
  is never called until `.roomService` is read.
- Bound in `container.ts` as `container.bind<Repository>(TYPES.Repository).to(AppRepositoryImpl).inSingletonScope()`
  and property-injected onto `BaseViewModel` as `repository` — see the
  DI section below for why property injection specifically.

If you add a fourth service, give it the same treatment: an eager
field (if it works under Jest, like `apiService`/`storageService`) or
a lazy getter (if it doesn't, like `roomService`) on
`AppRepositoryImpl` — never a fifth thing injected straight into
`BaseViewModel`.

## Local database: `app/data/local/room/` (scaffold, not wired into any screen yet)

A local SQLite database exists, mirroring `ai-project-android`'s Room
setup one-for-one (down to the same "interface + impl" split as
`ApiService`) — but it's **scaffolding with no real feature
attached**: no ViewModel actually calls `repository.roomService` yet.
It's reachable (`repository.roomService` is on every ViewModel via
`AppRepositoryImpl`), but accessing it is exactly what constructs
`RoomServiceImpl`/`AppDatabase` for the first time and opens the real
`expo-sqlite` connection — see the `Repository`/`AppRepositoryImpl`
section above for why that's a lazy getter, not eager.

- **`app/data/local/room/AppDatabase.ts`** — opens the SQLite
  connection (`expo-sqlite`'s `openDatabaseSync`), owns the schema
  (`CREATE TABLE IF NOT EXISTS`), and constructs the DAO(s) against
  that connection. Mirrors `AppDatabase.java`; Room's codegen would
  normally implement the DAO getter for you, here that's just
  `new UserDaoImpl(this.db)`.
- **`app/data/local/room/UserDao.ts`** — pure interface (CRUD
  signatures only), mirrors `DbUserDao.java`.
- **`app/data/local/room/UserDaoImpl.ts`** — the actual SQL, mirrors
  what Room's codegen would produce for `DbUserDao`.
- **`app/data/local/room/RoomService.ts`** / **`RoomServiceImpl.ts`**
  — thin facade over the database's DAOs, mirrors
  `RoomService.java`/`AppDbService.java` exactly (`userDao(): UserDao`
  delegating straight to `AppDatabase.getUserDao()`).
- **`app/data/model/room/UserEntity.ts`** — the row shape, mirrors
  `UserEntity.java` (a single `userId` column — this is genuinely all
  the Android reference has too).

Adding a new table follows the same shape: entity in
`data/model/room/`, DAO interface + impl in `data/local/room/`, add
its getter to `RoomService`/`RoomServiceImpl`/`AppDatabase`.

**Jest caveat:** `expo-sqlite` is a native module with no jest-expo
mock, so `container.get(AppDatabase)` / `container.get(TYPES.RoomService)`
— and, just as much, actually *reading* `repository.roomService` — crashes
under Jest (`NativeDatabase is not a constructor`). This is exactly
why `AppRepositoryImpl.roomService` is a lazy getter (see above): as
long as no ViewModel reads `this.repository.roomService`, its test never
touches `expo-sqlite` at all. `AppDatabase.test.ts` covers the one
file that does touch it by mocking the `expo-sqlite` module itself;
`UserDaoImpl.test.ts`, `RoomServiceImpl.test.ts`, and
`AppRepositoryImpl.test.ts` avoid it entirely by mocking their direct
collaborator (a fake `SQLiteDatabase`/`AppDatabase` object) instead of
touching the real module. If you wire `repository.roomService` into a
real ViewModel later, follow that same pattern in its test — mock at
the collaborator boundary, not by trying to make `expo-sqlite` itself
work under Jest.

## Dependency injection (InversifyJS)

Two injection styles are used, deliberately different:

- **Constructor injection** for everything except the shared
  `Repository`: a constructor parameter with **both** an `@inject()`
  token **and** a plain default value. For a concrete class, inject
  the class itself as the token — `constructor(@inject(Api) private
  api: Api = new Api())`. For an interface (TS interfaces don't exist
  at runtime, so there's nothing to use as a token), inject its
  `Symbol` from `app/di/types.ts` instead — see `Api`'s
  `@inject(AuthStore)`.
- **Property injection** for `repository` specifically: `BaseViewModel`
  declares `@inject(TYPES.Repository) protected repository!: Repository`
  as a class **field**, not a constructor param. Every ViewModel needs
  data-layer access, so this avoids every subclass re-declaring
  `@inject(TYPES.Repository)` in its own constructor and forwarding it
  via `super(repository)` — InversifyJS resolves property injections by
  walking the whole prototype chain, so a subclass gets it with **zero**
  DI code of its own (see `HomeViewModel`'s constructor — no
  `Repository` in sight). This is the one exception to "constructor
  injection everywhere"; don't extend the pattern to other shared
  dependencies without a similarly strong "every single subclass needs
  this" case — property injection is easy to overuse into "spooky
  action" DI. (`ApiService` and `RoomService` themselves are never
  injected directly into a ViewModel — see the `Repository`/
  `AppRepositoryImpl` section above.)

Constructor-injected fields/params carry a plain default value
(`= new Api()`, `= defaultAuthStore`, etc.) — that's deliberate, not
boilerplate, but **`repository` does not**, and the difference matters:

- For a **constructor param**, InversifyJS passes the resolved
  dependency as a real positional argument when going through the
  container, so a JS default parameter is simply never evaluated on
  that path — it only kicks in for manual construction (`new Api()` in
  a test) where nothing is passed. No cost in production, so keeping
  the default is free and convenient.
- For a **property injection**, InversifyJS constructs the instance
  first (running any field initializer unconditionally) and only
  assigns the resolved value afterward — a default value here would
  build a throwaway `AppRepositoryImpl` on every single
  `container.get(XViewModel)` call just to immediately discard it.
  That's why `repository` uses a **definite assignment assertion**
  (`repository!: Repository`, no initializer) instead: it satisfies
  `strictPropertyInitialization` without ever constructing anything.
- **In production**, `app/di/container.ts` resolves the real graph
  (`StorageService → AuthStore → Api → ApiServiceImpl` and
  `AppDatabase → RoomServiceImpl`, both gathered under
  `AppRepositoryImpl` → `ViewModel`) and screens pull their ViewModel
  through `useViewModel(XViewModel)` (`app/di/useViewModel.ts`)
  instead of `useState(() => new XViewModel())`, so `repository` is
  always assigned before use.
- **In tests**, `new XViewModel()` alone leaves `repository` unset (no
  default to fall back on) — there's nothing to reach into anymore, so
  don't `jest.mock("@/data/remote/api/ApiServiceImpl")`. Instead,
  construct a plain mock object literal and assign it directly:
  `const apiService = { getX: jest.fn() } as unknown as
  jest.Mocked<ApiServiceImpl>; (vm as unknown as { repository: {
  apiService: ApiServiceImpl } }).repository = { apiService }`. See any
  `*ViewModel.test.ts`'s `mockApiServiceOf()` helper for the exact
  pattern. `app/di/container.test.ts` is what actually proves the
  property injection wiring works end-to-end through `container.get()`
  — extend it if you add another property-injected dependency.

`BaseViewModel` needs `@injectable()` even though it's never bound in
the container itself — InversifyJS's base-class dependency scan
requires it to see the inherited property injection at all; omitting
it fails with `Missing required @injectable annotation in:
BaseViewModel` the moment any subclass is resolved through the
container.

Bindings live in two `ContainerModule`s under `app/di/modules/`, not
inline in `container.ts` — mirrors Dagger's `AppComponent` assembled
from separate `@Module` classes (`AppModule`, `FragmentModule`).
`container.ts` itself is just `new Container()` +
`container.load(dataModule, viewModelModule)`. Add a new binding to
whichever module matches the layer: `dataModule.ts` for a new
data-layer service, `viewModelModule.ts` for a new ViewModel (`bind(X).toSelf()`
inside the module's `new ContainerModule((bind) => { ... })` callback
— same binding calls as before, just inside a module instead of
directly on `container`). Three bindings are deliberately not
`toSelf()`, both in `dataModule.ts`:
`bind<ApiService>(TYPES.ApiService).to(ApiServiceImpl)` and
`bind<Repository>(TYPES.Repository).to(AppRepositoryImpl)`
(binding an interface token to its implementation), and `AuthStore`,
bound with `toConstantValue(authStore)` so it stays the same singleton
instance as the directly-imported `authStore` export — a fresh
`toSelf()` there would give the app two independent copies of the
auth token.

**A second base URL** (a different backend, not just a different
endpoint) is a real example here, not hypothetical:
`app/data/remote/api/master/` holds `MasterApiService.ts`/
`MasterApiServiceImpl.ts` — same interface + impl split as `ApiService`,
pointed at `Config.MASTER_API_URL` (a public demo API,
`jsonplaceholder.typicode.com`, standing in for "some other backend").
`Api` can't be `toSelf()` for both base URLs at once, so `dataModule.ts`
binds the second configured instance behind its own `TYPES.MasterApi`
Symbol: `bind<Api>(TYPES.MasterApi).toDynamicValue(() => new
Api(authStore, { url: Config.MASTER_API_URL, timeout: 10000
})).inSingletonScope()` — the same way Dagger would use a second
`@Named`/qualifier-bound `Retrofit` provider.
`MasterApiServiceImpl` then injects `@inject(TYPES.MasterApi)` instead
of the plain `Api` token `ApiServiceImpl` uses. `container.test.ts`
asserts the two resolved `Api` instances are different objects with
different `.config.url`s — that's what actually proves the two base
URLs don't collide, not just the binding code existing.
`MasterApiService` follows this project's `Repository` shape too in
spirit but isn't wired into it — it's standalone, reached only via
`container.get(TYPES.MasterApiService)` if something ever needs it.

Requires `import "reflect-metadata"` as the very first import in
`index.tsx` (and in `test/setup.ts` for Jest) — inversify's decorators
depend on it being loaded before anything else.

## The MVVM screen convention — READ THIS BEFORE ADDING A SCREEN

Every screen is its own folder under `app/screens/`. Two files, one
responsibility each:

- **`<ScreenName>Screen.tsx`** — the View **and** its styles, in one
  file: the component first, then every `$name: ThemedStyle<T> = ({
  colors, spacing, ... }) => ({ ... })` style constant below it (`const`,
  not exported — nothing outside this file needs them), applied via
  `themed($name)`. Resolves its ViewModel with
  `useViewModel(XViewModel)` (`@/di/useViewModel`), wraps the component
  in `observer()` from `mobx-react-lite` — skip `observer()` only if a
  screen truly has no ViewModel/observable state (`SplashScreen` is the
  one current example). No business logic, no direct
  `repository.apiService`/`repository.roomService` calls — only reads
  ViewModel fields and calls ViewModel methods.
- **`<ScreenName>ViewModel.ts`** — a MobX class extending `BaseViewModel`.
  All state and logic lives here, not in the View.

There is no separate `style.ts` and no `index.tsx` — the file is named
after the screen/component itself (`HomeScreen.tsx`, not `index.tsx`)
so it's identifiable by filename alone in an editor tab or a stack
trace, and imported by that name:
`import { HomeScreen } from "@/screens/Home/HomeScreen"`.

### The MobX subclassing gotcha (do not skip this)

`makeAutoObservable` **throws** on any class with a superclass (`"can
only be used for classes that don't have a superclass"`). Since every
ViewModel extends `BaseViewModel`, **never use `makeAutoObservable` in
a ViewModel** — always use `makeObservable` with explicit annotations
covering both the ViewModel's own fields and the inherited
`isLoading`/`error`:

```typescript
import { injectable } from "inversify"
import { actionBound, makeObservable, observable } from "mobx"

import { BaseViewModel } from "@/viewmodels/base/BaseViewModel"

@injectable()
export class HomeViewModel extends BaseViewModel {
  count = 0

  constructor() {
    super()
    makeObservable(this, {
      count: observable,
      isLoading: observable,
      error: observable,
      increment: actionBound,
    })
  }

  increment() {
    this.count += 1
  }
}
```

No `Repository`/`ApiService` import, no `@inject()`, no
`super(repository)` — every ViewModel needs data-layer access, so
`BaseViewModel` property-injects `protected repository: Repository` (see
the DI section above) and `this.repository.apiService`/`this.repository.roomService`
are just there, ready to use once you add a real endpoint. The only
thing every ViewModel's constructor still needs is `@injectable()` on
the class and a call to `makeObservable`.

Use **`actionBound`** (not plain `action`, and not `action.bound` —
this project's installed mobx version doesn't attach `.bound` to the
`action` function at runtime) for any method passed directly as an
event handler (e.g. `onPress={viewModel.increment}`). Plain `action`
methods lose their `this` binding when passed that way and crash on
first use; they're only safe when called from an inline arrow function
like `onPress={() => viewModel.doThing()}`.

If a ViewModel calls an API, add the endpoint following the steps in
the "`ApiService`: interface + impl, one DTO per file" section above
— **don't** create a new repository class per screen; every endpoint
is declared once on the `ApiService` interface, reached through the
one shared `Repository`. `this.repository.apiService` is already available on
every ViewModel (property-injected by `BaseViewModel`, see the DI
section above) — just call it through
`this.runAction(async () => { ... })`.

### Registering a new screen

1. Create `app/screens/<Name>/{<Name>Screen.tsx,<Name>ViewModel.ts}`.
2. Register the route in `app/navigators/MainTabNavigator.tsx` (bottom
   tab) or `app/navigators/AppNavigator.tsx` (stack-only screen), and
   add the matching entry to `app/navigators/navigationTypes.ts`.
3. Add its ViewModel binding to `app/di/modules/viewModelModule.ts`.
4. Add i18n keys to **both** `app/i18n/en.ts` and `app/i18n/vi.ts` —
   never hardcode user-facing strings, always go through `tx="..."` /
   `translate("...")`.

## Sub-components — same folder-per-unit convention, local first

A piece of UI worth its own file (a `FlatList` `renderItem` that's grown
non-trivial, a repeated block within one screen) is **not** written
inline inside a screen's `<Name>Screen.tsx` — but it also doesn't jump
straight to the shared `app/components/` folder. It stays **local to
the screen that owns it**, inside a `components/` subfolder next to
that screen's own files — mirroring the top-level `app/components/`
convention one level down, so the screen's own root
(`<Name>Screen.tsx`, `<Name>ViewModel.ts`) stays uncluttered:

```
app/screens/Wishlist/
  WishlistScreen.tsx        # the screen (component + its styles)
  WishlistViewModel.ts
  components/
    WishlistCard/
      WishlistCard.tsx         # local sub-component (component + its styles), only Wishlist uses it
```

Same one-file shape as a screen — the component and its `$name:
ThemedStyle<T>` style constants together in `<ComponentName>.tsx`, no
`index.tsx`; add a ViewModel only if the sub-component has its own
state/logic (most don't, since they just render from props). Import it
with a relative path from the owning screen:
`import { WishlistCard } from "./components/WishlistCard/WishlistCard"`.

**Promote to `app/components/<Name>/` only once a second screen
actually needs it.** Until then, keep it local — don't guess at reuse
that hasn't happened yet (YAGNI). When you do promote it: move the
folder under `app/components/`, switch every importer to the
`@/components/<Name>/<Name>` alias, and drop any props/behavior that
only made sense for the original screen.

## Auth infrastructure: kept, but nothing uses it yet

There is **no** Login screen and **no** auth gate in this base
project — `AppNavigator`'s `initialRouteName` is `Splash`, and Splash
always resets to `MainTabs` after a fixed delay (see
`SplashScreen.tsx`). What's still here, deliberately, is the plumbing
a real login screen would plug into:

- **`app/stores/authStore.ts`** — a MobX singleton (`@injectable()`,
  bound in `dataModule.ts` via `toConstantValue(authStore)` so every
  consumer shares one instance) holding `token`/`username` and
  `isAuthenticated`. Nothing calls `authStore.setToken()` anywhere in
  this project yet.
- **`Api`'s Bearer-token attachment** (`app/data/remote/api/index.ts`)
  — `addAsyncRequestTransform` reads `this.authStore.token` and, if
  set, attaches `Authorization: Bearer <token>` to every outgoing
  request. This is generic and has nothing login-specific baked in.

To add a real login screen later: create `app/screens/Login/` following
the MVVM convention above, add a `login(username, password)` endpoint
to `ApiService`/`ApiServiceImpl`, call `authStore.setToken(token,
username)` on success, and change `SplashScreen`/`AppNavigator` to
gate on `authStore.isAuthenticated` before deciding where to reset to
— that's the entire integration surface; nothing else in the DI graph
needs to change.

## Settings screen: language + theme

`app/screens/Settings/SettingsScreen.tsx` is the app's one stack-pushed
(non-tab) screen, reached from the gear icon in `HomeScreen`'s header
(`navigation.navigate("Settings")` — `Settings` is on `AppStackParamList`,
not `MainTabParamList`, so it isn't a tab). It's a pure UI screen with no
`ApiService`/`Repository` involved, so it has no ViewModel — it just reads
and writes two pieces of app-wide state that already exist elsewhere:

- **Theme (dark/light)** — a `Switch` bound directly to
  `useAppTheme().themeContext`/`setThemeContextOverride`; no new code needed
  here, that mechanism already existed (see the DI-adjacent theme section
  below). The app **defaults to dark** (`theme/context.tsx`'s
  `themeContext` fallback is `"dark"`, not the device's own color scheme) —
  `colors.ts`/`colorsDark.ts` were authored as a single dark UI, so there's
  no real second "light" look to fall back to.
- **Language (vi/en)** — `app/i18n/index.ts` exports `changeLanguage(tag)`
  (persists the choice to MMKV under `LANGUAGE_STORAGE_KEY` and calls
  `i18n.changeLanguage`) and `getCurrentLanguage()`. Two `Radio` rows call
  `changeLanguage`. This needed a workaround `Text`/`translate()` don't
  subscribe to i18next via `useTranslation()` — they call `i18n.t` directly,
  so nothing re-renders on its own when the language changes. Instead,
  `app.tsx` reads `LANGUAGE_STORAGE_KEY` via `useMMKVString` and passes it
  as `key={language}` on `<AppNavigator>`, so writing a new language remounts
  the whole navigator tree, and every `Text`/`translate()` call picks up the
  new `i18n.language` on that fresh render. `initI18n` also checks
  `LANGUAGE_STORAGE_KEY` first (before device-locale detection), so a
  manual choice survives an app restart.

If you add a third piece of app-wide, user-toggleable state to this screen,
follow the same shape: put the actual state in whatever module already owns
it (a context, MMKV, a store) rather than in a ViewModel here, and only
reach for a remount-via-`key` trick if that state feeds `translate()`/`Text`
directly instead of a React-subscribed hook.

## Logging and crash reporting

Mirrors ai-project-android's Timber + OkHttp `HttpLoggingInterceptor` +
Firebase Crashlytics setup:

- **`app/utils/logger.ts`** — `logger.d/i/w/e(tag, message, extra?)`, a
  tagged/leveled console logger. Only prints when `__DEV__` (mirrors
  `MyTimberDebugTree` only being planted in a debug build); `logger.e`
  additionally forwards to `reportCrash` outside of dev (mirrors
  `MyTimberReleaseTree` forwarding non-verbose logs to Crashlytics). Use
  this instead of a bare `console.log` anywhere you'd reach for one —
  it's the one already wired to disappear in a release build.
- **`app/data/remote/api/apiLogger.ts`** — `logApiCall`, attached via
  `this.apisauce.addMonitor(logApiCall)` in `Api`'s constructor
  (`app/data/remote/api/index.ts`), so both `Api` instances (the default
  one and `MasterApiService`'s second-base-URL one) get it automatically.
  Logs method/URL/status/duration/body for every request and response
  through `logger.d`, mirroring `AppModule.getClient()`'s
  `HttpLoggingInterceptor` at `Level.BODY` — the level toggle there
  (`BuildConfig.DEBUG` ? BODY : NONE) is `logger.d`'s own `__DEV__` gate
  here instead of a second interceptor config.
- **`app/utils/crashReporting.ts`** — `initCrashReporting()` (called once
  at the top of `app.tsx`) and `reportCrash(error, type?)` (called from
  `ErrorBoundary.componentDidCatch`). Uses
  `@react-native-firebase/crashlytics`'s modular API
  (`getCrashlytics()`/`log()`/`recordError()`/
  `setCrashlyticsCollectionEnabled()`, not the older default-export
  method-chaining style — check whichever's actually installed before
  copying this pattern elsewhere, the API shape has changed across
  major versions). Collection is only enabled outside of `__DEV__`.
  - **Needs a Firebase project you set up yourself** before it does
    anything at runtime: register this app's bundle id/package
    (`com.baseapp`, or whatever you rename it to) in the Firebase
    console, download `google-services.json` (Android) /
    `GoogleService-Info.plist` (iOS) to the project root (paths already
    wired in `app.json`'s
    `android.googleServicesFile`/`ios.googleServicesFile`), then run
    `expo prebuild` and rebuild natively (`expo run:ios`/`run:android`)
    — this is a native module, a Metro/JS-only reload can't pick it up,
    and skipping the config files entirely will crash the app at the
    `getCrashlytics()` call in `crashReporting.ts` the moment it loads.
  - `test/setup.ts` mocks `@react-native-firebase/crashlytics` (same
    reason `expo-sqlite` needs mocking — the native module doesn't
    exist under Jest); update that mock if you change which named
    exports `crashReporting.ts` uses.
  - **Two CocoaPods config-plugin fixes were needed for `pod install` to
    even succeed on iOS** (verified with a placeholder
    `GoogleService-Info.plist` — pod resolution doesn't care whether the
    Firebase project is real, only that a file is present at that path
    for Xcode to copy in):
    1. `@react-native-firebase/app`'s plugin defaults to resolving
       Firebase via Swift Package Manager, which conflicts with this
       project's static linkage (`pod install` fails: "SPM + static
       linkage is not supported"). Fixed by passing
       `{ "ios": { "disableSPM": true } }` to the plugin in `app.json`
       — this is the plugin's own documented escape hatch, injecting
       `$RNFirebaseDisableSPM = true` into `ios/Podfile`.
    2. Once Firebase resolves via CocoaPods instead, its Swift pods
       (`FirebaseCoreInternal`, `FirebaseCrashlytics`, `FirebaseSessions`)
       fail to build as static libraries against non-modular
       dependencies (`GoogleUtilities`, `nanopb`, `GoogleDataTransport`)
       unless `use_modular_headers!` is set globally in the Podfile.
       `expo-build-properties` has no option for this (only a per-pod
       `modular_headers` flag under `extraPods`), so
       **`plugins/withIosModularHeaders.js`** is a small local Expo
       config plugin that injects it — registered in `app.json`'s
       `plugins` array by file path. Don't hand-edit `ios/Podfile` to
       add this instead; it's regenerated by every `expo prebuild`.

## OTA update (`expo-updates`)

The Settings screen's "Update" section (`app/utils/appUpdates.ts` +
`SettingsScreen.tsx`) checks EAS Update's server for a newer **JS-only**
bundle and applies it without a store release — genuinely different from
a native rebuild, not just "download a new build automatically":

- `checkForUpdate()` guards on `Updates.isEnabled` first — that's
  `false` for any dev client/Expo Go build, or any build with no
  update channel configured (which is the state of this base project
  right now — see below), so the UI shows a distinct "disabled" status
  there instead of the native call throwing.
- `downloadAndApplyUpdate()` calls `fetchUpdateAsync()` then
  `reloadAsync()` to apply immediately, rather than waiting for
  `expo-updates`' own default (apply on next cold start).
- Only ever touches JS/assets — adding a native module (like Crashlytics
  above), changing permissions, or anything else in `app.json`'s
  `ios`/`android`/`plugins` sections needs an actual new native build
  (`eas build` + store submission or `expo run:ios`/`run:android`), an
  OTA update can't carry that.
- **Needs an EAS project linked to your own Expo account** — this base
  project deliberately has no `extra.eas.projectId`/`updates.url` in
  `app.json` (those were stripped since they're tied to a specific
  Expo account). Run `eas init` yourself (creates
  `extra.eas.projectId` and an `updates.url` pointing at
  `https://u.expo.dev/<project-id>`), then `eas update` to actually
  publish a JS bundle for the app to find. `runtimeVersion` is already
  set to `{ "policy": "appVersion" }` — bump `version` in `app.json`
  (and do a real native build) whenever a change needs a new runtime,
  since OTA updates are only offered to devices running a matching
  runtime version.

```bash

```

project.

## What NOT to do

- Don't add screens as bare files directly under `app/screens/` — every
  screen is its own folder, even a trivial placeholder, holding
  `<Name>Screen.tsx` (+ `<Name>ViewModel.ts` if it has state).
- Don't split a screen/component back into separate `index.tsx` +
  `style.ts` files — the component and its styles live together in one
  `<Name>.tsx` file.
- Don't put business logic in `<Name>Screen.tsx` — it belongs in the
  ViewModel.
- Don't use `makeAutoObservable` in a ViewModel (see above).
- Don't create a per-screen repository class — every endpoint is a
  signature on `ApiService` (`app/data/remote/api/ApiService.ts`),
  implemented in `ApiServiceImpl.ts`.
- Don't put apisauce calls or DTO-to-domain mapping in `ApiService.ts`
  — that belongs in `ApiServiceImpl.ts`; `ApiService.ts` stays
  signatures only.
- Don't inline a response/request shape as an unexported `interface`
  inside `ApiServiceImpl.ts` — give it its own file under
  `app/data/model/api/`.
- Don't construct a ViewModel with `new XViewModel()` inside a screen —
  use `useViewModel(XViewModel)` so it resolves through the DI
  container.
- Don't inject `ApiService`/`RoomService`/`StorageService` directly
  into a ViewModel — they only ever reach a ViewModel through
  `this.repository.apiService`/`this.repository.roomService`/
  `this.repository.storageService` (see `Repository`/`AppRepositoryImpl`
  above).
- Don't hand-edit `ios/`/`android/` — they're regenerated by prebuild.
- Don't hardcode user-facing text — always go through i18n.
- Don't re-add a Splash → Login auth gate without also wiring a real
  login screen — see "Auth infrastructure" above.
